# 다음 라운드 진행 메타 프롬프트 (폼 프리셋 Chrome Extension)

> **사용법**: `[메타 프롬프트 본문]`을 통째로 복사해 AI(에이전트)에 붙여넣으세요. AI는 **직전 라운드의 종료 상태를 확인하고, 다음 라운드의 후보를 요구사항 정의서(REQUIREMENTS.md) 기준으로 선정·평가한 뒤, 승인받은 작업을 워크트리 단위로 병렬 실행**합니다. 기능이 추가/변경되면 REQUIREMENTS.md도 함께 갱신합니다.
>
> **중점**: 매 라운드는 **상태 확인 → 후보 선정 → 평가 → 승인 → 실행 → 검증 → 보고**의 사이클. 코드 변경 전 반드시 사용자 승인을 받는다.
>
> **전제 조건**: 프로젝트 루트(`projects/my-chrome-extension/`)에서 실행. 작업 워크트리는 `orca/workspaces/my-chrome-extension/<브랜치명>/`에 존재.

## [메타 프롬프트 본문]

당신은 반복 개발(라운드) 진행 전문가입니다. 아래 Chrome 확장 프로그램(MV3) 프로젝트의 **다음 라운드**를 진행하세요. 절차를 반드시 순서대로 따르며, 3단계(계획 제시)에서 사용자 승인을 받기 전에는 코드를 변경하지 않습니다.

## 1. 직전 라운드 종료 상태 확인

1. `git log --oneline -10`, `git worktree list`, `git status --short` 실행
2. `.sisyphus/notepads/form-preset-extension/decisions.md`를 읽고 직전 라운드의 결정(D7, D8 등) 파악
3. `.sisyphus/plans/*.md`의 미완료 TODO(`- [ ]`)와 보류 항목 파악
4. **`REQUIREMENTS.md`(요구사항 정의서)를 읽는다**: R1~R8 구현 상태, §3 비기능 제약, §6 검증 체크리스트, §8 보류/미구현 항목 파악
5. 위 정보로 "직전 라운드가 끝난 시점의 기준선"을 한 단락으로 요약

## 2. 다음 라운드 후보 선정

미완료 TODO·보류 항목·정리 작업에서 **이번 라운드 후보**를 선정한다. 각 후보는 아래 정보를 갖춘다:

```
후보 <번호>: <한 줄 목표>
- 출처: <결정/플랜/이슈 중 어디서 왔는지>
- 범위: <변경될 파일·기능>
- 가치: <왜 지금 해야 하는지>
- 리스크: <기존 기능/데이터에 미치는 영향>
- 의존성: <선행 작업 여부>
```

### 이 프로젝트의 알려진 후보 풀 (참고 — REQUIREMENTS.md §8과 대조)

| 후보 | 출처 | 내용 |
|------|------|------|
| P1: 브라우저 E2E 테스트 | REQUIREMENTS.md §8 | Playwright 기반 확장 로드 수준 테스트 (playwright 미설치 — `npm install` 필요) |
| P2: 신규 기능 | REQUIREMENTS.md §8 / 미완료 TODO | 보류 항목 또는 새 요구사항. 선정 시 R1~R8과 충돌·중복 여부 평가 후 **REQUIREMENTS.md에 먼저 반영(제안)한 뒤 작업** |
| P3: 워크트리/브랜치 정리 | 직전 라운드 보고 | 머지 완료된 워크트리·브랜치 삭제 (완전 정리 방침) |

> 기능 추가/변경 후보는 REQUIREMENTS.md(기능 요약·데이터 모델·메시지·검증 체크리스트) 갱신을 작업 범위에 포함한다.

## 3. 후보 평가 & 계획 제시 (승인 필수)

1. 각 후보를 평가해 **이번 라운드에 포함할 것과 보류할 것**을 정한다.
   - **P1(암호화)** 포팅 시 핵심 설계 질문을 먼저 결정해야 한다 (사용자에게 제시):
     - 암호화 적용 범위: ① 필드 단위 `sensitive` 플래그(민감 필드만 암호화, 하위 호환) ② 전체 프리셋 일괄 암호화(스키마 전면 변경) ③ 보류
     - 기존 평문 데이터 호환: 저장된 평문 값은 어떻게 처리할지 (마이그레이션/그대로 둠)
   - **P2(옵션 페이지)**: master의 popup과 기능이 겹치면 보류, 고유 기능(예: 프리셋 목록 관리·복사)이 있으면 포함
   - **P3(정리)**: 단순 작업, 포함
2. 아래 형식으로 계획을 제시하고 **승인을 받는다. 승인 전 코드 변경 금지.**

```
# 다음 라운드 계획 (Round N)
## 병렬 실행
- UNIT 1: ... → 워크트리: <경로>
- UNIT 2: ... → 워크트리: <경로>
## 순차 실행 (의존)
- UNIT 3: ... 
## 보류
- 후보: 이유
## 완료 후
- 전체 검증 → 플랜·노트 갱신 → 머지 → 워크트리 정리
```

## 4. 실행 (병렬 디스패치)

- 승인된 후보를 **UNIT으로 분해**하고 워크트리에 매핑한다.
  - 기존 워크트리를 재사용하거나(`git worktree list`로 확인), 없으면 새로 만든다
  - 같은 워크트리에 2개 UNIT을 동시에 넣지 않는다. 결과 의존·스키마 의존이 있으면 순차로 묶는다
- 각 UNIT 에이전트 프롬프트에는 목표/성공 기준/변경 파일/필수 수행/금지 사항/참고 패턴을 명시한다.
- 공통 제약: **MV3 + 네이티브 JS, 한국어 UI**, 타입 오류 억제·빈 catch·테스트 삭제 금지, 할당 워크트리 밖 수정 금지.

## 5. 검증 & 통합

1. **독립 검증**: 각 워크트리에서 `node --check`, `lsp_diagnostics`, 성공 기준 충족 확인 (성공 기준은 REQUIREMENTS.md 요구사항 ID와 매핑된 것)
2. **base 동기화**: master로 rebase 후 재검증
3. **통합 검증**: master에 머지 → `npm run build` + 기존 테스트 실행 → 회귀 확인
4. **플랜·노트·요구사항 갱신**: 완료 TODO `[x]`, decisions.md에 이번 라운드 결정(D9부터) 기록, **기능이 추가/변경된 경우 REQUIREMENTS.md(기능 요약·데이터 모델·메시지·검증 체크리스트)도 함께 갱신**
5. **워크트리 정리**: 머지 완료된 워크트리 삭제 (사용자 지시 따름)
6. 실패 시 해당 에이전트 세션(`session_id`) 이어받아 수정 지시, 3회 연속 실패 시 중단·보고

## 6. 최종 보고 형식 (반드시 이 형식)

```
# Round N 완료 보고
## 실행 결과
- UNIT 1: ✅ / ❌ (근거)
- UNIT 2: ✅ / ❌ (근거)
## 통합 검증
- 머지: ✅ / ❌ / 빌드: ✅ / ❌ / 테스트: ✅ / ❌
- 플랜 갱신: N건 / 요구사항 정의서(REQUIREMENTS.md) 갱신: ✅ / ⏭️ 해당 없음 / 워크트리 정리: N개
## 다음 라운드(Round N+1) 후보
- [ ] 항목: 이유
## 이슈
- [설명] (출처)
```

## 기대 산출물 요약

```
직전 라운드 기준선 확인 → 후보 선정(P1~P3) → 평가 & 계획 제시 → 사용자 승인
→ 워크트리별 병렬 실행 → 단위 검증 + 머지 + 통합 빌드/테스트
→ 플랜·노트 갱신 + 워크트리 정리 → 완료 보고 + 다음 라운드 후보
```

각 라운드가 **명확한 완료 기준**을 갖고, 그 다음 라운드의 후보가 보고서에서 자연스럽게 나오는 것이 산출물입니다. 승인 없이 코드를 변경하지 않습니다.
