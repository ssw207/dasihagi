# 메타프롬프트 — 필드 저장 반응 속도

## 목표 (사용자 요구 원문 포함)
사용자: "필드 저장시 반응이 너무 느림"
→ 편집에서 필드 50개일 때 `저장` 클릭 후 토스트/목록 전환까지 체감이 느림. 저장 중 UI가 블로킹되거나, 저장 후 `loadPresets()`가 전체 프리셋을 복호화하느라 느림.

## 변경 범위 (파일별)
- `popup/popup.js` — `#btn-save-preset` 핸들러에 즉시 피드백(버튼 텍스트 `저장 중...`, 토스트 `저장 중...` 즉시) 및 로컬 낙관적 갱신으로 체감 속도 개선. 성공 후 `loadPresets()` 전체 재조회 대신 로컬 `presets` 배열에서 해당 프리셋만 교체 후 `renderList()`로 즉시 렌더, 백그라운드 재조회는 `requestIdleCallback`으로 지연.
- `background.js` — `savePreset` 자체는 이미 AES-GCM으로 빠르나, 50개 필드(≈10KB)도 10ms 내외. 별도 최적화는 불필요하나, `PRESET_UPDATE`가 `getPresetById`로 기존 프리셋을 한 번 더 복호화하는 부분을 캐시로 줄이는 것은 선택. 이번에는 팝업 체감 위주로.
- `dist/` — `npm run build`로 재생성
- 테스트 — `check`/`replay`/`qa` 영향 없음

## 구현 상세
### 팝업 체감 개선
- 저장 클릭 즉시 `btn.textContent = '저장 중...'` + `btn.disabled = true` + `showToast('저장 중...')` (이미 disabled지만 텍스트 변경으로 피드백)
- `await sendMessage({type:'PRESET_UPDATE',...})`는 그대로 대기하되, 성공 시 `showToast('저장되었습니다.')` 후 `backToList()` 대신 로컬 갱신:
  ```js
  const idx = presets.findIndex(p=>p.id===editingPreset.id);
  if (idx !== -1) presets[idx] = {...editingPreset, updatedAt: Date.now()};
  else presets.push(editingPreset);
  backToListOptimistic(); // editorView 숨기고 listView 보이고 renderList()만, loadPresets()는 호출 안 함
  // 백그라운드 정합성을 위해 idle 시 한 번 재조회
  if (window.requestIdleCallback) requestIdleCallback(()=>loadPresets(), {timeout:2000});
  else setTimeout(()=>loadPresets(), 500);
  ```
- `backToListOptimistic`은 기존 `backToList()`에서 `loadPresets()`를 뺀 버전 — `editorView` 숨기고 `listView` 보이고 `renderList()`만.
- 신규 생성 시에도 동일 — `resp.data`를 `presets.push` 후 즉시 렌더.

### MUST NOT 위반 방지
- 저장 실패 시에는 목록으로 이동하지 않고 에러 토스트만 — 기존 동작 유지
- 암호화/저장 로직 변경 금지 — 체감만 개선
- 필드 데이터 구조 변경 금지
