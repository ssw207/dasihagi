# 병렬 작업 진행 메타 프롬프트 (폼 프리셋 Chrome Extension — Orca 워크트리)

> **사용법**: `[메타 프롬프트 본문]`을 통째로 복사해 AI(에이전트)에 붙여넣으세요. AI는 **현재 진행 상황과 워크트리 상태를 파악한 뒤, 남은 작업을 요구사항 정의서(REQUIREMENTS.md) 기준으로 독립 단위로 분해해 각 워크트리에 별도 에이전트를 병렬로 실행**합니다. 각 단위의 완료 여부는 **REQUIREMENTS.md의 요구사항 ID(R1~R8)와 성공 기준을 대조**해 판정합니다.
>
> **중점**: 작업을 순차적으로 하지 않는다. **독립적인 작업은 반드시 동시에 진행**한다. **이 프로젝트에는 이미 워크트리가 존재**하므로, 워크트리 = 병렬 실행 단위로 사용한다.
>
> **전제 조건**: 본체 워크트리(`C:/Users/hoo kim/orca/projects/my-chrome-extension/`)에서 실행. 작업 워크트리는 `C:/Users/hoo kim/orca/workspaces/my-chrome-extension/<브랜치명>/`에 존재.

## [메타 프롬프트 본문]

당신은 병렬 작업 조율 전문가입니다. 아래 Chrome 확장 프로그램(MV3) 프로젝트의 **남은 작업을 찾아 독립 단위로 분해하고, 존재하는 워크트리에 별도 에이전트를 병렬로 실행**해 진행 상황을 전진시키세요. 모든 작업은 실행 전에 계획을 사용자에게 제시하고 승인받은 뒤 진행합니다.

## 1. 정보 수집 (진행 상황 + 워크트리 파악)

1. **git 상태**: `git log --oneline -15`, `git status --short`, `git branch -a`, `git branch --merged master` / `--no-merged master` 실행 → 완료/대기 기능 식별
2. **워크트리 상태**: `git worktree list` (또는 `orca worktree ps --json`) 실행 → 각 워크트리의 **경로, 브랜치, HEAD 위치** 기록
3. `.sisyphus/plans/*.md` 전체를 읽고 미완료 TODO(`- [ ]`)와 미머지 브랜치 목록 작성
4. `.sisyphus/notepads/**`(decisions/issues/problems/learnings)를 읽고 작업에 영향을 주는 결정·이슈 파악
5. 미완료 항목이 실제로 아직 필요한지 코드를 확인 (이미 구현됐는데 체크만 안 된 항목은 "완료 처리 대상"으로 분류)
6. **`REQUIREMENTS.md`(요구사항 정의서)를 읽는다**: R1~R8 구현 상태, §3 비기능 제약, §6 검증 체크리스트, §8 보류/미구현 항목을 파악하고, 이후 각 UNIT의 성공 기준을 요구사항 ID와 매핑한다

### 워크트리 위생 점검 (반드시 수행)

| 상태 | 판별 방법 | 처리 |
|------|-----------|------|
| 머지됐는데 워크트리가 남아 있음 | 워크트리 브랜치가 `git branch --merged master`에 포함 | 정리 대상으로 표시 (아직 다른 워크트리의 base일 수 있으므로 삭제 전 확인) |
| master보다 오래된 base에 있음 | 워크트리 HEAD가 master의 머지 커밋을 포함하지 않음 | **작업 시작 전 master로 rebase 필요** (병렬 실행 전에 선행 처리) |
| 자체 커밋이 있음 | 워크트리 브랜치가 master에 없는 커밋 보유 | 작업 진행 중으로 간주, master와의 차이(diff) 확인 |

## 2. 병렬 분해 (가장 중요한 단계)

미완료 항목을 **독립 단위(Unit)** 로 분해하고, **각 단위를 작업 워크트리 1개에 매핑**한다. 각 단위는 다음 6개 요소를 반드시 갖춘다:

```
UNIT <번호>: <한 줄 목표> → 워크트리: <workspaces/... 경로>
- 변경 파일: <구체적 경로 목록>
- 성공 기준: <검증 가능한 결과 — REQUIREMENTS.md의 요구사항 ID(R1-1 등)와 매핑>
- 의존성: <없음 | UNIT N 결과 필요>
- 필수 수행: <반드시 해야 할 것>
- 금지 사항: <절대 하지 말 것>
```

### 병렬 가능 여부 판별

**워크트리는 파일 수정이 물리적으로 분리되므로, 두 단위가 같은 파일을 건드려도 병렬 실행이 가능하다.** (충돌은 머지 시점에 해결) 다만 아래 경우는 병렬화에서 제외한다:

| 판별 질문 | 병렬 가능? |
|-----------|-----------|
| 두 단위가 **같은 워크트리를 쓰는가**? | ❌ 불가 (한 워크트리에 에이전트 1개) |
| 한 단위가 다른 단위의 **결과/커밋에 의존**하는가? | ❌ 불가 (순차 또는 base 동기화 후) |
| 단위가 **저장소 데이터 모델(스키마)**을 바꾸고, 다른 단위가 그 모델을 쓰는가? | ❌ 불가 (순차: 스키마 → 사용처) |
| 위 셋 다 아니면 (파일이 겹쳐도) | ✅ 병렬 실행 (워크트리 분리) |

- 의존 관계가 있으면 **순차 단계**로 묶는다. (예: 스키마 변경 → 그 스키마를 쓰는 UI)
- 한 번에 병렬로 실행할 단위는 **2~3개**를 권장한다. (머지 충돌·검증 부담 통제)
- **기존 워크트리가 없거나, 현재 워크트리와 매핑이 안 맞는 새 단위**가 생기면 `orca worktree create --repo id:<repoId> --name <task-name> --json`으로 새로 만든다.

## 3. 실행 계획 제시 & 승인

- 분해 결과를 아래 형식으로 사용자에게 제시하고 **승인을 받는다. 승인 전에는 코드를 변경하지 않는다.**

```
# 병렬 실행 계획
## 선행 작업 (병렬 실행 전, 순차)
- stale 워크트리 base 갱신: <워크트리 경로> → master rebase
- (필요 시) 새 워크트리 생성

## 병렬 실행 (동시, 워크트리별 에이전트 1개)
- UNIT 1: ... → 워크트리: <경로> (변경 파일, 성공 기준)
- UNIT 2: ... → 워크트리: <경로> (변경 파일, 성공 기준)

## 순차 실행 (의존)
- UNIT 3: UNIT 1 완료 후 ...

## 완료 후
- 전체 검증 → 플랜 체크박스 갱신 → 워크트리 머지 → 머지된 워크트리 정리 (삭제 여부는 사용자 지시)
```

## 4. 병렬 실행 (워크트리별 에이전트 디스패치)

- 승인 후 각 독립 단위를 **할당된 워크트리에서 별도 에이전트로 동시에(백그라운드) 실행**한다. 순차로 하나씩 하지 않는다.
- **각 에이전트는 반드시 자기 워크트리 경로를 작업 디렉터리로 사용**한다. 본체(`projects/my-chrome-extension/`)나 다른 워크트리를 수정하면 안 된다.
- 각 에이전트 프롬프트에는 6개 요소(목표/성공 기준/변경 파일/필수 수행/금지 사항/참고 패턴)를 **명시적으로 포함**한다. 애매한 프롬프트는 금지.
- 참고할 기존 패턴이 있으면 구체적으로 지시한다 (예: "기존 `popup.js`의 프리셋 CRUD 메시지 처리 패턴을 따라라", "`manifest.json`의 권한 선언을 확인하라").
- 공통 제약을 모든 에이전트에 주입한다:
  - 이 프로젝트는 **MV3 + 네이티브 JS(번들러 없음)**, 모든 UI 문자열은 **한국어**
  - 타입 오류 억제(`as any`, `@ts-ignore`), 빈 catch, 테스트 삭제로 "통과"시키는 행위 금지
  - 할당된 워크트리 밖의 파일 수정 금지, 다른 에이전트가 맡은 단위 간섭 금지
  - 실패하면 즉시 중단하고 원인과 증거(로그/스크린샷)를 보고

## 5. 검증 & 통합 (머지)

각 에이전트가 끝나면 **결과를 반드시 검증**한다. 에이전트가 "했다"는 말만 믿지 않는다.

1. **독립 검증**: 각 워크트리에서 변경 파일 문법 검사(`node --check`), `lsp_diagnostics`, 성공 기준 충족 여부 확인
2. **요구사항 대조 (REQUIREMENTS.md)**: 각 워크트리의 변경이 요구사항 ID에 대응하는지 확인한다. 어느 요구사항에도 대응하지 않는 변경, 또는 요구사항을 위반하는 변경(예: 민감 필드 평문 노출, UI 한국어 위반)이 있으면 해당 단위를 실패 처리하고 수정을 지시한다. 변경에 따라 요구사항이 추가/수정돼야 하면 작업 완료 시 REQUIREMENTS.md 갱신을 함께 요구한다
3. **base 동기화**: 작업 시작 전에 못 한 워크트리가 있으면 `master`로 rebase 후 다시 검증 (병렬 중 master가 움직였을 수 있음)
4. **통합 검증**: 워크트리 브랜치를 `master`에 머지한 뒤 본체에서 전체 빌드(`npm run build`) + 기존 테스트 실행 → 회귀 없는지 확인. **충돌이 나면 각 워크트리의 의도를 존중해 수동 해결**하고, 훼손된 부분이 없나 다시 검증
5. **플랜·노트·요구사항 갱신**: 완료된 TODO의 체크박스를 `[x]`로 표시, 노트(decisions/issues/problems)에 변경 사항 기록, **기능이 추가/변경됐으면 REQUIREMENTS.md(기능 요약·데이터 모델·메시지·검증 체크리스트)도 함께 갱신**
6. **워크트리 정리**: 머지된 워크트리 브랜치는 정리한다. `git worktree remove <경로>` 또는 `orca worktree rm --worktree id:<repoId>::<path> --force --json`. 삭제 여부는 사용자 지시를 따른다.
7. 실패한 단위가 있으면 해당 에이전트의 세션을 이어받아(`session_id` 재사용) 구체적 오류를 지적하며 수정을 지시한다. 3회 연속 실패 시 중단하고 사용자에게 상황을 보고한다.

## 6. 최종 보고 형식 (반드시 이 형식)

```
# 병렬 작업 완료 보고

## 실행 결과 (워크트리별)
- UNIT 1 (워크트리: <경로>): ✅ / ❌ (근거: 검증 명령 결과)
- UNIT 2 (워크트리: <경로>): ✅ / ❌ (근거: 검증 명령 결과)
- UNIT 3 (순차): ✅ / ❌ (근거)

## 통합 검증
- 머지: ✅ / ❌ (충돌 해결 N건)
- 빌드: ✅ / ❌
- 기존 테스트: ✅ / ❌ / ⏭️ 없음
- 플랜 갱신: [x] 처리한 항목 수 N개
- 요구사항 정의서(REQUIREMENTS.md) 갱신: ✅ / ⏭️ 해당 없음
- 워크트리 정리: 삭제 N개 / 유지 N개

## 남은 작업 (다음 병렬 라운드 후보)
- [ ] 항목: 이유

## 이슈
- [설명] (출처)
```

## 기대 산출물 요약

```
진행 상황 + 워크트리 상태 파악(플랜/git/worktree list) → 워크트리 위생 점검
→ 독립 단위 분해 & 워크트리 매핑 → 계획 제시 & 승인
→ 워크트리별 병렬 에이전트 실행 → 단위별 검증 + 머지 + 통합 빌드/테스트
→ 플랜·노트 갱신 → 머지된 워크트리 정리 → 완료 보고 + 다음 라운드 후보
```

순차 처리 대신 **기존 워크트리를 병렬 실행 단위로 활용**해 전체 완료 시간을 단축하는 것이 산출물입니다. 독립성이 없는 작업은 순차로 실행하며, 병렬화를 위해 코드 품질이나 워크트리 위생을 희생하지 않습니다.
