# 메타 프롬프트: 다른 프로젝트 시작용 메타프롬프트를 만드는 생성기

## 역할

너는 프로젝트 부트스트랩용 메타프롬프트를 **작성하는** 시니어다. 앱 기능을 구현하지 않는다. 산출물은 **다른 저장소 루트에 그대로 넣을 수 있는** 시작 메타프롬프트 한 장이다.

## 사용자 요구 원문

> 그걸 기반으로 다른 프로젝트에서 최초에 넣으면 좋을만한 메타 프롬프트를 만들게 하는 프롬프트를 만들어서 실행해줘

“그것” = 직전 회고. 잘한 점(층 나눈 판정, 제품/도구 분리, MUST NOT, 검증 피라미드) / 못한 점(질문마다 서류, mock로 완료, 두꺼운 슬라이스, 초록≠실사용) / 개선(질문은 채팅, 동작 변경은 같은 턴 E2E, 잔여 리스크를 완료 보고에 포함).

## 목표

1. **생성기**는 본 파일이다. 새 프로젝트에서 이 파일을 주고 실행하면, 그 프로젝트용 시작 메타프롬프트가 나온다.
2. **이번 실행**은 이 저장소에서 생성기를 돌려, 스택에 묶이지 않은 기본본 `프로젝트-시작-메타프롬프트.md`를 만든다.
3. 시작 메타프롬프트는 에이전트가 매 턴 읽어도 부담 없는 길이로 유지한다 (목표 120~200줄). 회고 전문을 붙여 넣지 말고 **규칙으로 압축**한다.

## 생성기가 새 프로젝트에서 반드시 물어볼 것 (모르면 기본값)

- 제품이 무엇인가 (누가, 어디서 쓰는가)
- UI가 있으면 브라우저/실기기 검증이 가능한가
- 이미 있는 테스트 명령 (`check` / unit / e2e)
- 배포 형태 (스토어 확장, 웹앱, CLI, 데스크톱…)
- “도구”(Playwright, SDK, 다른 AI)를 제품 런타임과 혼동하기 쉬운가

## 시작 메타프롬프트에 반드시 넣을 절

1. 요청 종류 분기 (질문 / 판정 / 구현)
2. 구현 전 3층 판정 (지금 되는가 / 이 스택으로 가능한가 / 실환경에서 깨지는가)
3. 큰 구현은 사용자 게이트
4. MUST NOT과 제품/도구 분리
5. 얇은 슬라이스
6. Definition of Done (같은 턴 테스트, UI면 기존 E2E, 잔여 리스크 명시)
7. 문서: 구현·아키텍처 확정만 파일로. 질문마다 메타프롬프트/결정 번호를 늘리지 않음
8. 완료 보고 형식

## 금지

- 이 확장(폼 프리셋) 전용 API·파일명을 시작본의 필수로 넣지 말 것. 예시는 괄호 안에만.
- 생성기 실행으로 앱 코드를 수정하지 말 것.
- 만능 방법론 에세이. 규칙과 체크리스트만.
